## 3. Phase 1：P0 生产高频痛点与表单校验缺陷修复

### Task 1.1 — Prometheus / Loki 时间戳单位归一化（修复 `unix-ms` 与 `now-1h` 400 错误）

- **优先级**：P0（生产实锤问题）
- **根因定位**：
  1. 内部工具口径分裂：[`grafana_list_annotations`](../../src/mcp/bridgeSchemas.ts#L418-L419) 要求 epoch **毫秒**，[`grafana_get_alert_history`](../../src/mcp/bridgeSchemas.ts#L407-L408) 要求 epoch **秒**，而 Prom/Loki 工具的 JSON Schema 未注明时间单位。
  2. [`QueryLimits.ts`](../../src/grafana/QueryLimits.ts#L166-L207) 的 `parseTimestamp` 虽然可识别 `unix-ms`（`1e12 <= ts <= 1e15`），但未在发送给上游前转为秒级；而 Prometheus HTTP API 仅认秒/RFC3339（传毫秒会报 400 或解析成远古/未来年份），Loki HTTP API 则会把 13 位数字当成**纳秒**（1970-01-01 附近）。此外 `now`、`now-1h` 等相对时间在 `parseTimestamp` 中返回 `undefined`，原样透传也会触发 400。
  3. 注意保护既有契约：[`test/grafana/QueryLimits.test.ts`](../../test/grafana/QueryLimits.test.ts#L63-L72) 明确断言 `clampQueryTimeRange` 自身保留原格式（包括 `unix-ms`），且对 `-1h` 保持原样不截断。因此应保持 `clampQueryTimeRange` 现有行为不变，而在构造上游查询或 `planQueryLimits` 出口统一执行归一化。

- **涉及文件**：
  - 修改：`src/grafana/QueryLimits.ts`
  - 修改：`src/grafana/typedDatasourceQueries.ts`
  - 修改：`src/grafana/typedDatasourceDiscovery.ts`
  - 修改：`src/mcp/bridgeSchemas.ts`
  - 测试：`test/grafana/QueryLimits.test.ts`、`test/grafana/typedDatasourceQueries.test.ts`、`test/grafana/typedDatasourceDiscovery.test.ts`、`test/mcp/bridgeSchemas.test.ts`

- **具体实施步骤**：
  1. **在 `src/grafana/QueryLimits.ts` 中新增相对时间解析与归一化辅助函数**：
     - 匹配 `^now(?:-(\d+(?:\.\d+)?(?:ms|s|m|h|d|w|y)))?$`（复用已有 `parseDurationSeconds`）：`now` 解析为 `nowMs`，`now-<dur>` 解析为 `nowMs - durSeconds * 1000`。
     - 导出 `normalizeDatasourceTimestamp(raw: string, nowMs = Date.now()): string`：
       - 若为 `rfc3339` 或 `unix-seconds` 或 `unix-nanos`（Loki 纳秒级保留精度）：原样返回（或经范围校验）。
       - 若为 `unix-ms`（`1e12 <= numeric <= 1e15`）或相对时间 `now` / `now-<dur>`：转换为 **Unix 秒级字符串**（`String(Math.floor(epochMs / 1000))`；若对 `start`/`end` 有亚秒需求可保留整数秒，Prometheus/Loki 均稳定兼容）。
       - 无法识别的字符串原样返回，交由下游或上游显式报错。
     - 在 `planQueryLimits` 内部（或紧接 `applyRangeLimits` 之后）：对已识别出的 Prometheus 端点（`prometheus-range`、`prometheus-instant`）及 Loki 端点（`loki-range`、`loki-instant`），分别对 `query.start`、`query.end`、`query.time` 调用 `normalizeDatasourceTimestamp(val, input.now)`（注意 Loki `query_range` 支持纳秒及秒级，转秒级对 Loki 同样安全合法）。
     - **兼容性检查**：不要改变 `clampQueryTimeRange()` 自身对 `unix-ms` 保留毫秒输出的语义，确保 [`test/grafana/QueryLimits.test.ts`](../../test/grafana/QueryLimits.test.ts#L63-L72) 现有断言 100% 通过。
  2. **在 `src/grafana/typedDatasourceQueries.ts` 与 `src/grafana/typedDatasourceDiscovery.ts` 接入归一化**：
     - 在 `buildPrometheusProxyCall` 与 `buildLokiProxyCall` 中，对传入的 `start`、`end`、`time` 调用 `normalizeDatasourceTimestamp`（支持传入可选 `now` 参数以便单测固定时间）。
     - 在 `typedDatasourceDiscovery.ts` 的 `timeQuery()` 中同样对 `start`、`end` 调用 `normalizeDatasourceTimestamp`。
  3. **更新 `src/mcp/bridgeSchemas.ts` Schema 描述**：
     - 在 `GRAFANA_QUERY_PROMETHEUS_INPUT_SCHEMA`、`GRAFANA_QUERY_LOKI_INPUT_SCHEMA` 与 `discoveryTimeAndRegexProperties` 的 `start`/`end`/`time` 属性中补充 `description`：
       `"Timestamp as Unix seconds (recommended), RFC3339, or relative expression like \"now-1h\" (epoch milliseconds are automatically converted to seconds)."`

- **验收标准 & 验证命令**：
  - 传入 `start: "1700000000000"`（13 位毫秒）调用 `buildPrometheusProxyCall` / `buildLokiProxyCall` / `planQueryLimits` 后，输出参数为 `"1700000000"`（10 位秒）。
  - 传入 `start: "now-1h"`, `end: "now"` 时，能正确计算 `epochMs` 并受 `maxRangeMs` 限流截断保护，输出合法 Unix 秒级字符串。
  - 执行：
    ```bash
    npx vitest run test/grafana/QueryLimits.test.ts test/grafana/typedDatasourceQueries.test.ts test/grafana/typedDatasourceDiscovery.test.ts test/mcp/bridgeSchemas.test.ts
    ```

## 4. Phase 2：P1 安全只读边界、TOFU 并发控制与子路径兼容

### Task 2.1 — TOFU 证书确认 Singleflight 并发弹窗合并 + 确认后再启动 Socket 15s 超时

- **优先级**：P1（TLS 首次连接核心体验与竞态 Bug）
- **根因定位**：
  1. 首次展开未信任的自签名 HTTPS 实例时，[`DashboardTreeProvider`](../../src/tree/DashboardTreeProvider.ts#L256-L259) 与 [`AlertTreeProvider`](../../src/tree/AlertTreeProvider.ts#L175-L179) 会通过 `Promise.all` 并发发出多个请求。此时连接池无可用空闲连接，多个 Socket 同时触发 `createInteractiveCertVerifier.verify()`，导致连续弹出 2～4 个重复模态确认框。
  2. [`GrafanaHttpClient.performRequest`](../../src/grafana/GrafanaHttpClient.ts#L307-L366) 在 `client.request()` 创建阶段即传入 `timeout: 15_000`。当 `attachCertVerification` 挂起等待用户在模态框中核对指纹超过 15 秒时，底层 Socket 触发 `timeout` 被销毁并归类为 `network` 错误，进而触发 `DEFAULT_RETRY_BACKOFF_MS` 再次自动重试弹窗。

- **涉及文件**：
  - 修改：`src/grafana/createInteractiveCertVerifier.ts`
  - 修改：`src/grafana/GrafanaHttpClient.ts`
  - 测试：`test/grafana/createInteractiveCertVerifier.test.ts`、`test/grafana/GrafanaHttpClient.test.ts`

- **具体实施步骤**：
  1. **在 `src/grafana/createInteractiveCertVerifier.ts` 中加入基于 `WeakMap` 的 Singleflight 去重**：
     - 定义模块级 `const inFlightByStore = new WeakMap<GrafanaCertTrustStore, Map<string, Promise<boolean>>>();`（使用 `WeakMap` 绑定 `trustStore` 实例，既能让同一扩展内的多处 `createInteractiveCertVerifier(certTrustStore)` 调用共享锁，又不会污染不同单测之间各自构造的 `MemoryMemento` 仓库）。
     - 在 `verify(host, port, fingerprint256)` 中：
       - 先查 `await trustStore.check(host, port, fingerprint256)`，若已是 `'trusted'` 立即返回 `true`。
       - 若需交互弹窗（`'unknown'` 或 `'changed'`），构造 key = `${host}:${port}|${fingerprint256}`。
       - 若 `storeInFlight.has(key)`，直接 `return storeInFlight.get(key)!`。
       - 否则创建弹窗与写库 Promise，存入 `storeInFlight`，并在 `.finally(() => storeInFlight.delete(key))` 中清理。
  2. **在 `src/grafana/GrafanaHttpClient.ts` 中延迟启动 Request 超时计时器**：
     - 在 `performRequest` 中：
       - 当 `usesCertVerifier` 为 `true` 时，传给 `client.request` 的选项中**暂不设置 `timeout`**（或设为 `0`），避免等待 TLS TOFU 交互确认期间被 15s 定时器打断。
       - 在 `attachCertVerification` 的 `onVerified` 回调内，先调用 `request.setTimeout(this.options.timeoutMs ?? DEFAULT_TIMEOUT_MS)`，然后再执行 `writeAndEnd(request, bodyText)`。
       - 注意保留原 `request.on('timeout', ...)` 监听器，确保一旦确认完成开始发送请求，网络读写超时（15s）照常生效；若无 `certVerifier`（`usesCertVerifier === false`），保持构造时立即设置 `timeout` 不变。

- **验收标准 & 验证命令**：
